# Чеклист проверки автотеста (BDD / Vanessa Automation)

Универсальный чеклист для проверки качества автотеста перед отправкой на ревью или мерж-реквест. Применим к любому проекту на Vanessa Automation; пункты, зависящие от конкретного окружения/команды, помечены как «настраиваемые» и должны быть уточнены локально.

---

## 1. Структура и организация теста

### 1.1. Наименования
- Названия сценариев и шагов информативны и отражают выполняемые действия (не «Кейс1», «Шаг2»).
- Название сценария содержит порядковый номер (например `Сценарий: 01_Название`).
- Пользователи, переменные и параметры именованы понятно.
- Путь к файлу отражает суть теста, без пробелов.

### 1.2. Разделение сценариев
- Каждая отдельная проверка вынесена в отдельный сценарий.
- Сценарии независимы друг от друга.
- Слишком сложные сценарии декомпозированы (при необходимости — на несколько feature-файлов).

### 1.3. Повторное использование
- Перед созданием экспортного сценария проверено, что аналогичного ещё нет.
- Повторяющийся код (более 2 раз) вынесен в переиспользуемые (экспортные) сценарии.

### 1.4. Структура feature-файла
- Задан язык фичи: строка `#language: ru` и базовый тег структуры `@tree`.
- Проставлен тег отбора для запуска в пайплайне (из конфигурации запуска / списка тегов проекта); новый тег создаётся только после добавления в эту конфигурацию.
- Ссылки на задачи/требования оформлены в шапке фичи (закомментированы); новые ссылки добавляются там же.
- Размер фичи не более ~1000 строк (иначе — вынести повторяющиеся блоки или разбить на несколько файлов).

### 1.5. Кодировка и теги запуска
- Кодировка файла — UTF-8 (с BOM, если требуется инструментарием).
- Если файл содержит переиспользуемые сценарии — проставлен тег `@ExportScenarios`.
- Тег базы/окружения запуска проставлен, если это требуется для прогона (настраиваемое правило конкретного проекта).

### 1.6. Переиспользуемые (экспортные) сценарии
- Расположены в каталоге переиспользуемого кода проекта или в `.Export` (для общих сценариев).
- Содержат необходимые теги: `@tree`, `@ExportScenarios` и, при необходимости, исключение из CI-прогона.
- Название начинается с префикса `(экспорт)`, например `Сценарий: (экспорт) подключаю клиент тестирования`.
- Имя уникально в рамках проекта; параметры передаются в кавычках.
- Параметры внутри шага экспортного сценария обрамлены квадратными кавычками `"[...]"`.
- В шапке экспортной фичи описано, для каких тестов она применяется (кроме файлов в `.Export`).

## 2. Стиль и оформление

### 2.1. Форматирование
- Отступы перед шагами — табуляция.
- Все группы шагов, кроме сценариев, начинаются с отступа.
- Используются группы шагов (например `* Открываю`).
- Названия групп начинаются с глагола 1-го лица настоящего времени («Открываю», «Создаю», «Заполняю», «Проверяю»).
- Перед группой шагов — одна пустая строка, перед сценарием — две.
- Таблицы Gherkin выровнены; лишние/пустые колонки и строки удалены.

### 2.2. Комментирование
- Неочевидные процессы пояснены комментариями (символ `//`).
- Комментарии к фиче расположены в шапке, под ссылками на задачи.
- Закомментированные шаги имеют пояснение и срок возврата/удаления.

### 2.3. Переменные
- Имена переменных — без пробелов, в едином стиле.
- Различаются локальные переменные сценария (`$Переменная$`) и глобальные/сессионные (`$$Переменная$$`).
- Глобальные переменные удаляются после использования; не используются шаги массового удаления всех глобальных переменных.

## 3. Качество шагов

### 3.1. Проверки
- Каждый значимый результат сопровождается проверкой.
- После проведения документа/операции добавлена проверка корректности выполнения.
- После открытия окна/формы добавлена проверка содержимого (не пустое «открылось окно»).
- Проверяются сообщения пользователю и уведомления.

### 3.2. Работа с формами и элементами
- Вместо фиксированных пауз — шаги с ожиданием («я жду открытия…», «я жду закрытия…»), где это возможно.
- Где возможно — «открылась форма» вместо «открылось окно» (быстрее сообщает об ошибке).
- «Накликанные» шаги проверены на необходимость и удалены, если не нужны.
- Для выбора значений используется поиск по строке/фильтр, а не закэшированные значения.
- Спецсимволы экранируются обратным слэшем `\` либо используются кавычки другого типа (`'...'`).

### 3.3. Условия и циклы
- Избегаются сложные вложенные конструкции, где возможно.
- В циклах добавлены проверки результата после завершения.

### 3.4. Запрещённые конструкции (без крайней необходимости)
- Не используются шаги «Пауза» и остановки всех сценариев.

### 3.5. Проектирование шагов и сценариев
- В шагах/сценариях не более 3 параметров; при большем числе применяется параметр-таблица.
- Параметры имеют понятные названия (не «Пар1», «Ф32»).
- Ключевые слова ДАНО / КОГДА / ТОГДА используются по логическому назначению (входные данные / действия / результат).
- Однотипные сценарии с разными входными данными оформляются через таблицу «Примеры:».
- Печатные формы проверяются по внешним макетам, а не по таблицам Gherkin.

---

## 4. Тест-клиент и пользователи

### 4.1. Подключение и запуск
- Используется стандартный/переиспользуемый сценарий подключения.
- Для прогона в CI исключаются шаги, требующие аппаратных привязок/лицензий (настраиваемый параметр запуска проекта).
- Дополнительное подключение к другой базе допускается только в исключительных случаях (через параметр строки соединения).

### 4.2. Завершение
- В конце сценария (при смене пользователя/окружения) клиент тестирования закрывается.
- Последний сценарий завершает процессы клиентов тестирования.

### 4.3. Пользователи
- Пароли и чувствительные данные не захардкожены в тесте; берутся из настроек/переменных окружения.
- У новых пользователей корректно заполнены учётные данные (полное имя, имя для входа) и разрешён вход.
- Новому пользователю выданы необходимые права доступа.

---

## 5. Критерии успеха

### 5.1. Готовность к CI
- Тест не зависит от данных и не оставляет данных, которые после прогона становятся невалидными.
- Отсутствуют шаги, не нужные для прохождения в пайплайне.

### 5.2. Завершение и очистка
- Есть отдельный сценарий завершения без номера (`Сценарий: Завершение сценариев`).
- Все изменения базы/окружения возвращены к исходному состоянию.
- Временные (глобальные) переменные удалены после использования.
